# PV Layout MVP Functional Specification

Work item: [PRODUCT-001 / PVOS Issue #12](https://github.com/8nt7h6k229-png/PVOS/issues/12)

Status: Proposed for PM approval

Product flow: **Geometry → Placement → Result**

## 1. Product Overview

The PV Layout MVP produces a deterministic rectangular PV panel layout for one user-selected roof partition.

The user supplies the roof geometry and partition, assigns a Local Axis, and selects the PV module parameters. The product generates panel positions within the selected partition and returns panel geometry, panel count, installed capacity, and placement warnings.

The MVP defines a bounded planning result. It does not detect roofs, create partitions, optimize placement, or perform electrical, structural, construction, cloud, collaborative, or AI-assisted design.

This specification defines product behavior without prescribing software architecture, technology, interface framework, or internal component design.

Evidence:

- [PM-003 MVP Definition](../PM/MVP_DEFINITION.md) defines the smallest evidenced workflow as an explicit polygonal partition, Local Axis, module parameters, deterministic contained placement, and result summary.
- [PM-003 Product Baseline](../PM/PRODUCT_BASELINE.md) establishes the deterministic 2D placement boundary.
- [PM-004 Project Charter](../PROJECT_CHARTER.md) requires explicit scope, deterministic and reviewable outcomes, and no silent capability promotion.

## 2. User Story

As a PV layout user, I want to provide roof geometry, select a user-defined partition, assign its layout direction, and select module parameters so that I can generate a repeatable panel layout and review its geometry, panel count, installed capacity, and placement warnings.

The user remains responsible for supplying the roof polygon and partitions. The MVP does not interpret an image, infer a roof, recognize regions, or divide the roof automatically.

### Product success criteria

A user can:

- load roof geometry;
- select a partition;
- assign a Local Axis;
- select a PV module;
- generate a deterministic layout;
- see panel geometry;
- see panel count;
- see installed capacity; and
- see placement warnings.

## 3. Functional Workflow

The complete user workflow is:

1. **Load roof geometry.** The user supplies a two-dimensional roof polygon in a consistent coordinate system.
2. **Provide roof partitions.** The user supplies one or more polygonal partitions associated with the roof geometry. No partition is generated by the product.
3. **Select a partition.** The user chooses exactly one partition as the placement boundary for the current layout operation.
4. **Assign a Local Axis.** The user specifies the Local Axis origin and rotation for the selected partition.
5. **Select PV module parameters.** The user supplies module dimensions, module power, horizontal and vertical gaps, and edge margin.
6. **Generate the layout grid.** The product evaluates rectangular panel candidates in the selected partition's local coordinate system.
7. **Validate candidates against the boundary.** A candidate is accepted only when its complete panel rectangle is contained by the selected partition.
8. **Place accepted panels.** Accepted candidates are returned as ordered panel geometry in the original roof coordinate system.
9. **Present the layout result.** The product presents panel geometry, panel count, installed capacity, and any placement warning.

The same valid inputs shall produce the same ordered panel result, statistics, and warnings.

## 4. Inputs

### 4.1 Roof geometry

| Input | Requirement |
|---|---|
| Roof polygon | One user-supplied, closed two-dimensional polygon represented by at least three distinct vertices |
| Coordinate system | All roof, partition, and Local Axis coordinates use the same global coordinate system |
| Linear unit | Millimetres |

The roof polygon provides the geometry context presented to the user. The selected partition is the operative placement boundary.

### 4.2 Roof partitions

| Input | Requirement |
|---|---|
| Partition identifier | A value that uniquely identifies the partition within the current input set |
| Partition boundary | A user-supplied, closed two-dimensional polygon represented by at least three distinct vertices |
| Selection | Exactly one supplied partition is selected for one layout operation |

The product shall not derive, split, merge, adjust, or recognize partitions automatically. If the roof is treated as one placement area, the user may supply that same polygon as the single partition.

### 4.3 Local Axis

| Input | Requirement |
|---|---|
| Origin | One two-dimensional point in the shared global coordinate system |
| Rotation | An angle in degrees defining the local positive X direction relative to the global positive X direction |

### 4.4 PV module parameters

| Input | Requirement |
|---|---|
| Module width | Positive value in millimetres; aligned with local X |
| Module height | Positive value in millimetres; aligned with local Y |
| Horizontal gap | Non-negative value in millimetres between adjacent module columns |
| Vertical gap | Non-negative value in millimetres between adjacent module rows |
| Edge margin | Non-negative value in millimetres applied to the local grid envelope |
| Module power | Rated power in watts supplied by the selected module and used to calculate installed capacity |

Module orientation is represented by the supplied width and height. Automatic portrait/landscape comparison is not part of the MVP.

### 4.5 Input validity

Layout generation proceeds only when:

- a partition is selected;
- roof and partition coordinates use the stated unit;
- the selected partition is a valid polygon;
- a Local Axis origin and rotation are supplied;
- module width and height are positive; and
- gaps and edge margin are non-negative; and
- the selected module supplies its rated power.

Invalid inputs shall not produce a partial layout result. The product shall identify the invalid input so the user can correct it.

## 5. Layout Result

One layout operation returns one result associated with the selected partition.

### 5.1 Panel geometry

For every accepted panel, the result contains:

- a unique, deterministic panel identifier;
- four ordered corner points defining the rectangular panel polygon; and
- corner coordinates transformed back into the original global coordinate system.

Panel geometry shall reflect the selected Local Axis and the supplied module width and height.

### 5.2 Panel count

The result contains the total number of accepted panels. The count equals the number of panel geometries in the result.

### 5.3 Installed capacity

The result contains installed capacity in kilowatt-peak, calculated as:

`installed capacity (kWp) = panel count × module power (W) ÷ 1000`

No inverter, string, loss, efficiency, or electrical-routing factor modifies this value.

### 5.4 Warnings

When no panel fits inside the selected partition with the supplied module and margin settings, the result contains a placement warning stating that no panels fit.

The no-fit condition is a valid zero-panel result, not a partially generated layout.

## 6. Geometry Definitions

### Roof polygon

The user-supplied two-dimensional polygon representing the overall roof geometry presented for the workflow. It is not detected or interpreted by the product.

### Roof partition

A user-supplied polygonal placement region associated with the roof geometry. The selected roof partition is the sole containment boundary for the current layout operation.

### Global coordinate system

The coordinate system in which the user supplies roof geometry, partitions, and the Local Axis origin, and in which panel geometry is returned.

### Local coordinate system

The partition-specific coordinate system defined by the Local Axis. The layout grid is rectangular and aligned with its X and Y directions.

### Panel rectangle

A four-corner polygon whose local X dimension equals module width and whose local Y dimension equals module height.

### Local grid envelope

The axis-aligned bounding rectangle of the selected partition after transformation into local coordinates, reduced on each side by the supplied edge margin.

The MVP concerns straight-edged 2D polygons and rectangular panels. Curves, bulges, three-dimensional geometry, polygon repair, and general geometry operations are outside scope.

## 7. Local Axis Definition

The Local Axis controls panel alignment independently for each selected partition.

It consists of:

- a global origin point; and
- a rotation angle in degrees.

The positive local X direction is the global positive X direction rotated by the supplied angle. The positive local Y direction is perpendicular to local X in the positive rotational convention.

For layout generation:

1. The selected partition is interpreted in the Local Axis coordinate system.
2. Module width and horizontal gap apply along local X.
3. Module height and vertical gap apply along local Y.
4. Accepted panel corners are returned in global coordinates.

Changing only the Local Axis may change panel positions and panel count. Reusing the same Local Axis and all other inputs shall reproduce the same result.

## 8. Layout Rules

1. Layout is generated for exactly one selected partition per operation.
2. Panels are rectangles aligned to the partition's Local Axis.
3. The candidate grid begins at the minimum local X and Y of the partition's local bounding rectangle plus the edge margin.
4. The grid's maximum local X and Y limits equal the maximum local extents minus the edge margin.
5. Horizontal candidate pitch equals module width plus horizontal gap.
6. Vertical candidate pitch equals module height plus vertical gap.
7. Rows are evaluated from lower to higher local Y.
8. Within each row, candidates are evaluated from lower to higher local X.
9. A candidate is evaluated only when its complete width and height fit within the local grid envelope.
10. A candidate becomes a panel only after satisfying all boundary rules.
11. Accepted panels retain their deterministic row-and-column evaluation order.
12. Panel identifiers are assigned sequentially in accepted order and remain stable for identical inputs.

The MVP does not search alternative origins, rotations, module orientations, or arrangements to increase panel count.

## 9. Boundary Rules

1. The selected user-supplied partition is the placement boundary.
2. Every accepted panel rectangle shall be fully contained within that partition.
3. A panel may touch the partition boundary and remain contained.
4. A panel that crosses or extends beyond the partition boundary shall be rejected as a complete candidate; it shall not be clipped or reshaped.
5. Rejected candidates shall not appear in panel geometry, panel count, or installed capacity.
6. The edge margin reduces the local grid envelope before candidates are evaluated.
7. The MVP does not calculate setbacks from rules, obstacles, shading, walkways, neighboring regions, or automatically recognized roof features.
8. If all candidates are rejected or the usable grid envelope cannot contain one module, the result contains zero panels and the no-fit warning.

## 10. Statistics

The MVP presents only the following layout statistics:

| Statistic | Definition |
|---|---|
| Panel count | Number of accepted panel geometries |
| Installed capacity | Panel count multiplied by module power and divided by 1000, expressed in kWp |

Statistics are derived from the returned panel result. They shall not include estimated energy yield, losses, performance ratio, string quantities, inverter loading, structural loading, cost, or optimization scores.

## 11. Acceptance Criteria

### 11.1 Workflow acceptance

The MVP is functionally acceptable when a user can:

1. load a supplied roof polygon;
2. provide and select one supplied roof partition;
3. assign a Local Axis origin and rotation;
4. supply valid module dimensions, gaps, edge margin, and module power;
5. generate the deterministic layout;
6. inspect panel geometry in global coordinates;
7. inspect panel count;
8. inspect installed capacity; and
9. inspect the no-fit placement warning when applicable.

### 11.2 Determinism acceptance

Given identical valid inputs, repeated layout operations shall return:

- the same accepted panel geometries;
- the same panel order and identifiers;
- the same panel count;
- the same installed capacity; and
- the same warnings.

### 11.3 Geometry and boundary acceptance

- Every returned panel is rectangular in the Local Axis coordinate system.
- Every returned panel has the supplied module width and height.
- Every returned panel is fully contained by the selected partition.
- No rejected or partial candidate is included.
- Returned corners are expressed in the original global coordinate system.

### 11.4 Result acceptance

- Panel count equals the number of returned panel geometries.
- Installed capacity follows the formula in §5.3.
- A valid result with no accepted panel has a count and installed capacity of zero and contains the no-fit warning.
- A valid result with one or more accepted panels does not contain the no-fit warning.

### 11.5 Scope acceptance

Acceptance of this specification does not include:

- roof detection or automatic region recognition;
- automatic partition generation;
- AI or optimization;
- alternative-orientation search;
- obstacles, shading, walkways, or rule-derived setbacks;
- electrical routing or string design;
- structural analysis;
- construction drawings;
- runtime dashboards;
- cloud collaboration or multi-user behavior; or
- any capability classified as planned, future, branch-only, or not evidenced by the approved product baseline.

Evidence: [PM-002 Branch Product Knowledge Map](../PM/BRANCH_PRODUCT_KNOWLEDGE_MAP.md), [PM-003 Product Scope](../PM/PRODUCT_SCOPE.md), [PM-003 Product Capability Matrix](../PM/PRODUCT_CAPABILITY_MATRIX.md), and [PM-004 Project Charter](../PROJECT_CHARTER.md).
